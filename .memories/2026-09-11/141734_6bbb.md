## Live indexes deleted twice during the hybrid-auto evaluation

**WHAT:** All ten corpus index directories under `~/.julie/indexes` were gone before Task 2 started (registry rows intact). Later, both julie checkout indexes (`julie_5cb3ea69`, `hybrid-auto_cfbab7d1`) vanished during the second gate run, and every corpus `facts.sqlite` was reborn at 14:10 to 14:13 UTC when the restarted service reopened each repo. Two corpus indexes (jq, newtonsoft) lost their vectors and re-embedded.

**WHY it matters:** Every evaluation after a restart or a `full` tier run starts cold and pays about 45 minutes of backfill. The second semantic-auto evidence run (scorecard `2026-09-11T14-13-10Z`, head-to-head `20260911T141321Z`) is invalid for that reason.

**HOW found:** `stat` birth times on facts.sqlite, registry `last_indexed`, `workspace_cleanup_events` (only `missing_path` rows; no orphan-dir events), vector counts on disk versus registry.

**Suspects (not proven):**
- `open_or_recreate` in `src/tools/workspace/indexing/store_open.rs` and `julie-runtime/src/workspace/mod.rs` deletes the whole `indexes/<id>/` on ANY open failure, including a transient one such as a 5 s busy timeout while the previous service process is still writing vectors.
- Force reindex in `src/handler.rs` around line 959 deletes the primary workspace index dir. A test that runs it in-process with the real `JULIE_HOME` and cwd at the checkout would delete the live index. The CLI test bucket already writes 36 rows per run into the live registry, so some tests do run against the live home.
- No service log file was found under `~/.julie` or the checkout to confirm which path fired.

**IMPACT:** Registry hygiene (brief item 2) must also cover: never delete an index on a transient open error; tests must never see the real `JULIE_HOME`; the service needs a log file.
