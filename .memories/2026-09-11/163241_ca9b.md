## Task 5 fix round 1: remove test now reads the indexes dir from its own registry database

**WHAT** — `test_remove_workspace_uses_global_index_dir_shape` and `test_remove_current_primary_workspace_is_blocked_in_process` (`src/tests/tools/workspace/global_targeting/global_remove.rs`) no longer build the index path from `RegistryPaths::new()`. Both use `daemon_db.indexes_dir().join(&workspace_id)`. The `HOME` / `USERPROFILE` swap and the now-unused `use crate::paths::RegistryPaths;` in `src/tests/tools/workspace/global_targeting.rs` are gone.

**WHY** — The lead gate failed on `tools-workspace-targeting`. `remove` reported success, but the directory the test watched still existed.

**HOW** — Task 5 made `registry_store_for` derive the indexes directory from the database it receives (design decision 5). The test opened `daemon.db` in a temp dir, so production deleted `<temp>/indexes/<id>`, while the test watched `$JULIE_HOME/indexes/<id>`. `.cargo/config.toml` now pins `JULIE_HOME` to `target/test-julie-home`, so the test's fake `HOME` no longer moved that path at all. The test carried the old coupling; the product path is the designed one.

**IMPACT**
- The remove test is hermetic: it creates and deletes only inside its own `TempDir`, never inside the shared `target/test-julie-home`.
- The blocked-remove assertion stopped being vacuous. It had been guarding a directory that production code never looks at.
- No product code changed. All five production `DaemonDatabase::open` sites pass `RegistryPaths::registry_db()`, so `<db parent>/indexes` still equals `RegistryPaths::indexes_dir()`.

**Evidence** — both tests pass by exact name; `cargo check --workspace --all-targets` clean.
