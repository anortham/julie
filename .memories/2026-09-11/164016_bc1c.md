## Task 6: cleanup sweep at service start

**WHAT** — `ServiceApp::serve` now spawns one background cleanup sweep right after it writes `service.json`. Two new private functions in `src/service/mod.rs`: `sweep_registry` (logs the three summary counts at `info!`, logs a failure at `warn!`) and `cleanup_sweep` (opens `DaemonDatabase` at `registry_paths.registry_db()`, builds the store with `registry_store_for`, runs `run_cleanup_sweep` with an empty `WorkspaceCleanupActivity`).

**WHY** — Dead registry rows and orphan index directories only got pruned when someone called `manage_workspace list`. A long-lived machine service could accumulate both forever. The plan asks for the same sweep once per service start.

**HOW**
- The sweep runs in a `tokio::spawn`, so it never blocks the bind or the first request.
- `WorkspaceCleanupActivity::new(HashSet::new())` is correct here: the service has no in-process live workspace set at bind time, and the activity stubs report zero watcher refs.
- Task 5's database-derived indexes dir means the sweep can only ever touch the indexes tree that belongs to the registry database it opened.
- Test helper `Running::start_in(home, idle)` was added so a test can seed the registry before the service starts; `Running::start` now delegates to it.

**IMPACT** — `service_start_prunes_dead_registry_rows_in_the_background` passes. A restart now prunes a workspace row whose path is gone and deletes an unregistered index directory, while leaving a live row and its index directory untouched.
