## Task 1 fix round 3: a silent repair failure and a cached empty store

Two review findings on the "delete only on version mismatch" work.

**WHAT**
- `src/request_engine/runtime_factory.rs`: both service bind paths dropped the startup repair result with `.ok()`. They now pass the result to a new `warn_on_repair_failure(index_root, outcome)`, which logs one WARN naming the index root and the error.
- `src/tools/workspace/indexing/store_open.rs`: `open_or_recreate` returns `OpenedCheckout { store, rebuilt }` instead of a bare store.
- `src/handler.rs`: `checkout_store_for_workspace` skips the `ref_store_cache` insert when the store was rebuilt after a version mismatch.

**WHY**
- Round 2 made a failed store open return an error and deleted the old `warn!`. An operator then got no log, no repair, and no delete.
- Round 1 routed `checkout_store_for_workspace` through the deleting opener. Read-only callers (health checker, health data plane, tool context snapshot) wiped a secondary checkout index, then cached the empty store for the rest of the session, so the checkout looked empty even after its owner reindexed it.

**HOW**
- The warn message carries the path and the error inline, not as tracing fields: the dashboard `ErrorBuffer` layer keeps only the `message` field, so structured fields never reach the operator's dashboard.
- Skipping the cache was chosen over scheduling an index run. `ProcessFairScheduler` is dormant (only re-exported, no caller), and a foreign handler must not write another checkout's index. The checkout's own handler heals the empty store: `plan_primary_workspace_repair` sees zero paths and returns `EmptyDatabase`.

**IMPACT**
- A read path can no longer pin an empty snapshot of another checkout for the session.
- A repair scan that does not run is now visible in the log and the dashboard.
- Tests: `dropped_repair_failure_is_logged_with_the_index_root`, `a_rebuilt_checkout_store_is_not_cached_empty`. The `store_open` module is 7 tests, all passing.
