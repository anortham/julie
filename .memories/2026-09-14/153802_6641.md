## WHAT

The `v8.0.0` GitHub release workflow built and verified all four platform archives, created the public release, uploaded all eight archive/checksum assets, then failed its public-asset verification on the Windows checksum file. Added `release_asset_verifier_accepts_windows_binary_checksum_marker` in `xtask/tests/toolchain_contract_tests.rs` and updated `.github/scripts/verify-release-assets.py` to accept the standard GNU binary-mode `*filename` marker while still enforcing the exact filename and SHA-256.

## WHY

The Windows runner's `sha256sum` emitted `HASH *julie-v8.0.0-x86_64-pc-windows-msvc.zip`. The archive's actual SHA-256 exactly matched the hash and GitHub asset digest; the verifier falsely required a bare filename and mislabeled the valid asset as corrupt.

## HOW

Downloaded the public release assets to a repo-local audit directory, independently hashed every file, and reproduced the verifier failure. Wrote the regression test first and observed the expected failure, applied the minimal parser fix, then observed the exact test pass. The fixed verifier passed against the actual public assets; `cargo fmt --all -- --check` and `git diff --check` passed. An independent Luna review found no correctness or compatibility issues.

## IMPACT

The public `v8.0.0` release and its four archives are valid, and its release notes exactly match `docs/release-notes/v8.0.0.md`. The failed release run skipped plugin publication. Next: commit/push this future-release verifier fix without moving the already-published v8 tag, then safely invoke and verify the plugin update from the valid public release.
