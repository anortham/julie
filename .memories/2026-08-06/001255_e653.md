## Wrote the julie-extractors v2.16.0 to v2.27.0 upgrade plan

Plan doc: `docs/plans/2026-08-05-julie-extractors-v2.27.0-upgrade.md`. Findings are compile-verified in an isolated worktree, not inferred.

### WHY
Julie is pinned to extractors v2.16.0 (2026-07-18); upstream is at v2.27.0 — 11 releases behind.

### HOW — empirical, not inferred
Re-pinned in a throwaway worktree and drove `cargo check --workspace --all-targets` to a **clean compile**, then built `julie-server` and indexed a C# fixture to observe real output change.

### KEY FINDINGS

**1. The six-manifest trap.** The pin is duplicated in root Cargo.toml + 5 crate manifests. Bumping only the root puts TWO extractor versions in the graph and yields **335 misleading errors** (expected ExtractionResults, found julie_extractors::ExtractionResults). Bump all six and the real count is **39 errors**.

**2. Break surface is small and mostly tests.** Four breaks:
- `Relationship` gained `span` + `reference_site_is_exact` — **35 sites / 19 files**
- `StructuredPendingRelationship` gained `reference_site_is_exact` — 1 site
- `with_span` split into `with_context_span` / `with_target_span` — 2 sites
- `ParseDiagnostic` gained `message` — 1 site

Only **4 true production files**: julie-core/database/helpers.rs, julie-pipeline/resolver.rs, julie-tools/navigation/fast_refs.rs and target_workspace.rs. The rest is test fixtures.

**NOT breaks (verified):** the ExtractFn/ExtractionLevel change never reaches Julie (calls go through ExtractorManager); ParseDiagnosticKind::DepthTruncated is harmless (diagnostics are serde JSON, message is serde(default)); no enum variants added to SymbolKind/RelationshipKind/Visibility.

**3. THE BIG ONE — silent stale index.** `EXTRACTION_CONTRACT_VERSION` is **byte-identical at all 13 tags** v2.16.0 to v2.27.0. Julie's reindex trigger keys on it via `SEMANTIC_INDEX_ENGINE_VERSION`, so re-pinning alone means `semantic_index_engine_refresh_needed()` returns false and every already-indexed file keeps v2.16.0-shaped rows forever. The guard test in src/tests/core/engine_version.rs gives a **false green** — it only asserts `contains(EXTRACTION_CONTRACT_VERSION)`, which stays true. Remedy: bump SEMANTIC_INDEX_ENGINE_VERSION by hand and make the test assert the pinned tag.

Runtime proof the output really changed — C# fixture indexed with the v2.27.0 binary gave 6 symbols where v2.16.0 gave 3: a new `namespace App.Core` symbol (v2.19.0 file-scoped namespaces), `Fixture` now parented to it (parent_symbol_id CHANGED), plus `requested` and `scale` as Variable symbols (v2.20.0 C# locals/parameters).

**4. Languages 36 to 38** (erlang, xml). Discovery is automatic — Julie derives extensions from `julie_extractors::language::supported_extensions()`. But Julie has only **34 embedded per-language search configs**; erlang and xml are missing (jsx/tsx are aliased, so fine). XML also missing from DOC_LANGUAGES and NON_EMBEDDABLE_LANGUAGES. Julie's docs claiming "34 languages" were already wrong by 2 before this upgrade.

**5. Verification gap.** `extractor-dep-integration` is in the **full tier only** — `cargo xtask test changed` and `dev` will NOT run it after a re-pin. Must prescribe the bucket explicitly. (The two hardcoded-v2.16.0 tests ARE caught by dev via the xtask-runner bucket.)

### POLICY CONFLICT
HEAD commit 8593ed71 formally **retires** Julie: "v7.17.0 is the final release", open items wontfix. README explicitly says extraction development continues upstream "which Miller consumes at a newer version than Julie's final pin". Executing this plan contradicts published policy — flagged as a decision for the owner (un-retire / one-off maintenance drop / don't execute). Miller is unaffected: it consumes the julie-extract CLI binary + SQLite artifact (.NET, pinned 2.20.0), not the Rust library. Julie is the only library-level consumer.

### IMPACT
The upgrade is roughly 8-9 agent tasks over 2-3 sessions. A compile-verified migration patch is saved at the scratchpad path v2.27.0-migration.patch (570 lines) — Task 2 is largely pre-solved.
