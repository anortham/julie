# Julie versus Miller replacement assessment

Reviewed Julie `eabf93cb`, Miller `3ed3920b`, and julie-plugin `db4dd894`. This is an assessment, not an implementation or release qualification. Source and live tool findings are separated from historical measurements. No product code was changed, no live service was restarted, and no regression suite or new controlled head-to-head was run.

I recommend Julie as the long-term code intelligence engine, with a staged replacement of Miller. I would not retire Miller or recommend the current revival to ordinary users yet. Julie's search and inspection results justify the direction; watcher recovery, request isolation, installation qualification, and several useful Miller workflows remain unfinished.

The production design is sensible: a small stdio client connects to one machine service, which owns separate checkout stores, watchers, SQLite facts, and Tantivy search. A native child process supplies optional embeddings. MCP, the JSON API, and the dashboard share the request engine. This avoids keeping two independent intelligence implementations alive indefinitely. Both products use the current extractor family, so parser breadth alone is not a differentiator.

The strongest findings, in priority order:

1. **High: watcher repair is disconnected.** Queue overflow and failed store writes set `needs_rescan`, but `QueueRuntime::run_cycle_with_retry_age` only processes queued events. The current watcher module has no consumer that performs the promised rescan. A failed or dropped batch can therefore leave stale search results until explicit refresh, startup reconciliation, or a later relevant event. Restore recovery through the production checkout-store path and test eventual freshness after overflow and write failure. Source-confirmed control-flow defect; no fault-injection repro was run during this assessment. Evidence: [watcher cycle](../../crates/julie-runtime/src/watcher/runtime.rs), lines 136–148; [failed apply](../../crates/julie-runtime/src/watcher/runtime/processing.rs), lines 212–239; [overflow](../../crates/julie-runtime/src/watcher/events.rs), lines 208–227.

2. **High: time-only deduplication can discard a real save.** `process_queue_batch` drops created/modified events if the same path was processed less than one second earlier. It does not compare content or retain the newest event. Saves straddling adjacent processor ticks can trigger this; two events already queued before one disk read usually do not. Coalesce pending changes by path or use the existing content hash rather than equating a short interval with identical content. The missing repair consumer makes this more serious. Evidence: [processing](../../crates/julie-runtime/src/watcher/runtime/processing.rs), lines 80–117. Source-confirmed; timing repro remains a required implementation test.

3. **High: concurrent requests can change each other's semantic behavior.** `RequestEngine::execute` sets a provider and `semantics_disabled` on the cached shared handler according to each request. An `off` request can clear the provider and set the flag after a concurrent `required` request passes readiness, but before its search reads the provider. That search can fail despite having passed readiness. Keep execution policy in request context and preserve the shared provider independently. This is a source-proven reachable interleaving, not an observed stress-test failure. Evidence: [dispatch](../../src/request_engine/dispatch.rs), lines 147–174; [provider lookup](../../src/handler.rs), lines 706–724; [runtime reuse](../../src/request_engine/runtime_factory.rs), lines 140–157.

4. **High for upgrades: archive extraction can fall back to an old executable.** The plugin launcher catches extraction failure, checks whether an executable exists, and launches that executable. It logs the fallback and does not mark the new archive extracted, so this is not a false successful extraction; nevertheless the user can remain on the old version. Windows executable locks are the obvious trigger, but the catch handles other extraction failures too. Its preflight stops the legacy daemon rather than the v8 service. Versioned extraction directories or an explicit stop/update/restart sequence would be safer; a failure should name the recovery action and actual running version. Evidence: [plugin launcher](../../../julie-plugin/hooks/run.cjs), lines 112–157, 160–211, 249–286. Native Windows reproduction was not run.

5. **Medium: reference output discards precision already available upstream.** Julie deduplicates by `(file_path, line)` and constructs results with `span: None` and `reference_site_is_exact: false`. Distinct calls on the same line can collapse, and definition lines pre-seeded into the deduplication set can hide a same-line use. This is insufficient evidence for exact renaming or exhaustive site counts. Preserve site identity, spans, and certainty, then distinguish exact references from inferred graph links. Evidence: [fast_refs](../../crates/julie-tools/src/navigation/fast_refs.rs), lines 300–351; Miller's [trace contract](../../../miller/src/Miller.Server/Tools/TraceTool.cs), line 56.

6. **Medium: default conceptual retrieval is a poor fit for some document searches.** Live `fast_search(query="workspace routing", file_pattern="docs/**")` selected semantic search and returned Python evaluation symbols. The same query with `backend="lexical"` returned `docs/WORKSPACE_ARCHITECTURE.md` immediately. Backend selection considers the query, not the requested file scope. Keep semantic defaults for code concepts, but give documentation, literal, and configuration retrieval a reliable content path. Evidence: [backend selection](../../crates/julie-tools/src/search/backend.rs), lines 21–36, and the live paired queries from this review. This is a relevance failure, not a claim that the filter was ignored: those Python files really are under `docs/`.

7. **Medium: lifecycle complexity exists without governing production.** The service uses `request_engine::RuntimeFactory`, whose runtime map has no eviction and holds its write lock while initializing a cold checkout. Warm lookups can wait behind that initialization. Separate `WorkspaceRuntimeManager` and fair-scheduler machinery are not the service's production path. Consolidate ownership rather than adding a third manager. Add bounded retention and cold-initialization isolation where the service actually acquires runtimes. Evidence: [factory](../../src/request_engine/runtime_factory.rs), lines 48–55 and 125–190; [service construction](../../src/service/mod.rs), lines 58–60; [separate manager](../../src/workspace_runtime/manager.rs). Historical multi-checkout memory observations are warnings, not a fresh leak measurement.

8. **Medium: release success does not establish installation success.** The release workflow's `Verify Release` step prints an asset list; it does not inspect the uploaded archives or execute their contents. Plugin update is dispatched without waiting for the downstream workflow. A successful server release can coexist with failed plugin distribution. Check archive contents and binary startup on each native target, verify the published asset set, and wait for plugin publication plus a clean-install smoke check. Evidence: [release workflow](../../.github/workflows/release.yml), lines 209–231. Existing pack-script tests remain valuable, but they do not replace native artifact checks.

Planning follow-up correction: a deeper source check found existing [web call-path traversal](../../crates/julie-tools/src/navigation/call_path_web.rs), including `WebRoute` and `SqlQuery` edges and unmatched endpoint reporting. The earlier review understated this capability. Its current limitations include suppressing all unmatched client calls when a symbol has any matched route and choosing the first client-call line for a matched hop. These need precise evidence and tests, not a replacement subsystem.

Historical Miller telemetry recorded about 83% of calls in search and inspect, 3.1% in content, and 0.4% in continuous testing. That favors replacing the navigation core first. Specialized tools can be infrequent but important, so call share alone is not a deletion criterion. See [tool-contract comparison](2026-09-10-tool-contract-comparison.md). The approved two-week naming/telemetry window remains sensible; there is no measured reason to rename everything now.

Sources: [paired retrieval matrix](2026-09-11-head-to-head-miller.md) and [later semantic-default run](2026-09-11-hybrid-auto-backend.md), especially its final section. The later default run skipped Miller, so it is not a new simultaneous head-to-head. These are small, warm, single-machine, file-level retrieval measurements. They do not prove end-to-end task completion, exact reference correctness, cold-start behavior, or all-language parity. The matrix also scores one selected expected path; valid alternative files can be counted as misses. Keep the useful evidence, expand the workload, and avoid a blanket speed multiplier.

For deployment, retain one supported launcher that starts the machine service automatically, and package the native sidecar beside the server. Manual binary users should still receive all essential tool guidance through MCP. The plugin currently adds Node 22.5+ as an installation prerequisite; make that cost explicit and retain a clear native archive path. The embedding model is a separate first-run download, so installation needs an honest distinction between lexical readiness and full semantic readiness, including download failures and offline operation.

Upgrade handling needs particular attention. `try_connect` rejects a healthy service with a different version. That is a defensible compatibility policy, but a newly installed client can fail against the old service, and surviving old shims can fail after the service changes. The supported upgrade flow must coordinate service replacement and client reconnection, verify versions, and state when a harness restart is necessary. Evidence: [service client](../../src/service/client.rs), lines 95–154.

Agent instructions should have one authoritative source, delivered in layers:

1. The first part of MCP `instructions` states explicit workspace targeting, how to open a workspace, and the basic search/inspect workflow.
2. Tool schemas and descriptions carry local requirements and examples; paging examples preserve workspace and filters.
3. Plugin hooks repeat essential guidance for supported clients and subagents. Skills supply longer task recipes when needed.
4. A clean-install check verifies what a real agent received and which tools it actually chooses. Shipping a file does not prove that a client loaded it.

Julie already compiles [JULIE_AGENT_INSTRUCTIONS.md](../../JULIE_AGENT_INSTRUCTIONS.md) into the binary and returns it during initialization through [mcp_adapter](../../src/handler/mcp_adapter.rs), lines 44–58. Preserve this. Official [Codex MCP documentation](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) confirms that Codex reads initialization instructions and recommends making the first 512 characters self-contained. Julie's workspace rule is currently near the end. Move it to the opening instructions. Essential guidance should survive without hooks; longer skills need not all occupy every agent's context.

There is an important distinction in the workspace findings. Current source **does** mark `workspace` required for the nine scoped MCP tools in `mcp_tool`, lines 255–280. Optional internal Rust fields are not proof of a broken public schema. This review's already-loaded tool catalog nevertheless advertises the older optional/default-primary contract. Its `manage_workspace health` example failed with `WORKSPACE_REQUIRED`; supplying `workspace_id` succeeded. Treat this as a demonstrated client-guidance/version-coherence problem and an operation-specific management guidance gap, not a reason to remove explicit routing.

The instruction to trust tools should also have a bounded exception for unavailable indexes, visible staleness, missing evidence, and incomplete output. “Never re-verify” is too absolute while the system has known freshness gaps. Prefer the tools, report the limitation, then use a targeted fallback when the tool cannot supply the evidence. Updating the surrounding Miller-specific agent routing is part of migration; otherwise old guidance continues steering agents toward Miller.

Release preparation must account for both repositories. Julie's local main contains the deployment work but is 188 commits ahead of its recorded origin/main. Plugin main is ahead seven and behind one because its distribution workflow replaces history with an orphan commit. Its local version manifests still read 7.18.0 pending the release workflow. Publish the reviewed v8 plugin launcher/workflow before dispatching a server release that depends on it, then verify downstream completion. Do not treat ahead/behind counts alone as a normal merge recipe for that repository.

Read-only GitHub checks during this review confirmed that `v8.0.0` has no public release, the latest Julie release is `v7.18.1` from 2026-08-20, and public plugin main remains `09a2c23`, the v7.18.1 distribution commit. Local revival progress is therefore not yet the installation experience normal users receive.

The replacement sequence I would choose is: repair watcher freshness and semantic request isolation; preserve exact reference evidence and fix document retrieval; qualify cold start, upgrades, and instruction delivery on the four supported native targets; use Julie by default for a real dogfood window; then retire or port the specialized Miller workflows based on task evidence. Include searches, explanations, edits, rapid saves, concurrent agents, worktrees, restarts, and offline model startup. Measure completed tasks, retries, output size, freshness, and resource use, not just fast successful tool calls.

Repository state was preserved. Julie began with a modified `.codex/config.toml` and an unrelated untracked memory file. The merged deployment worktree retains generated untracked fixture data; the plugin retains an untracked Linux archive. This assessment adds only this report and a memory checkpoint. Previous full-gate evidence was recorded at `cda68bed`, with 2,221 development, 13 CLI, and 69 dogfood tests plus 22 plugin tests. That is historical evidence, not a claim that this review reran or expanded those tests. Fresh native macOS/Windows artifacts, clean plugin installs, and deterministic reproductions of the newly identified concurrency/recovery defects remain required before release qualification.
